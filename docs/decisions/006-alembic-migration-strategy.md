# 006 — Alembic as the only schema-management strategy

**Status:** Accepted
**Date:** 2026-10-06
**Deciders:** Basel

## Context

Phase 1 introduces six tables, two Postgres ENUM types, CHECK constraints, and unique indexes. Schema will keep changing (Phase 4 adds trigram indexes, Phase 5 adds `vector` columns). We need a way to evolve the schema that is:

- versioned in git
- reproducible from an empty database
- reviewable in PRs
- safe to run in CI and on a laptop

`SQLAlchemy.MetaData.create_all()` is tempting because it is one line.

## Options considered

### Option A — `Base.metadata.create_all()` at startup
- **Pros:** zero extra tooling; models *are* the schema.
- **Cons:** cannot rename a column (it will add a new one and leave the old); cannot add a CHECK constraint to an existing table cleanly; no history; production and a coworker's laptop can silently diverge; ENUMs and extensions are easy to miss.

### Option B — Alembic, with autogenerate treated as a draft
- **Pros:** every schema change is a numbered, reviewable file; `alembic upgrade head` on an empty DB is a reproducible bootstrap; downgrade exists when we need it; CI can apply the same migrations the laptop does.
- **Cons:** two sources of truth (models + migrations) that can drift; autogenerate is imperfect, especially for Postgres ENUMs and `pgvector`.

### Option C — Hand-written SQL files run in order
- **Pros:** no Alembic learning curve; SQL is explicit.
- **Cons:** we reinvent Alembic's version table, upgrade/downgrade, and "already applied" tracking. Worse than using the tool built for this.

## Decision

**Option B.** Alembic owns schema changes. `create_all()` is allowed only as a convenience in isolated unit-test fixtures that do not claim to represent production. The first migration is **hand-written**, not autogenerated, because it creates ENUMs and extensions.

## Why

1. **ENUMs.** Alembic autogenerate does not reliably emit `CREATE TYPE` / `ALTER TYPE ... ADD VALUE`. Hand-writing the first migration lets us declare `node_type` and `edge_type` once, by name, and never recreate them on later autogenerates (`create_type=False` on the SQLAlchemy Enum).
2. **Reviewability.** A PR that adds a column shows a migration file. A reviewer can see the SQL. `create_all()` hides that.
3. **Empty-database bootstrap.** `alembic upgrade head` is the documented way to go from zero to the current schema. CI integration tests use exactly that path — the same path a new developer uses.

## Autogenerate: when it is safe, what still needs a human

Safe-ish as a *starting draft* when:

- adding a nullable column
- adding an index
- adding a new table that only uses already-created enum types

Always needs a human, even if autogenerate produced something:

- anything touching a Postgres ENUM (add value, rename, drop)
- column rename vs. drop-and-add (autogenerate often picks drop-and-add, which loses data)
- `CHECK` constraint wording
- `pgvector` columns (autogenerate does not know the `vector` type)
- data migrations mixed with schema migrations

Rule: **never commit an autogenerated file without reading the `upgrade()` and `downgrade()` functions.**

## Trade-offs

| We give up | We accept this because |
|---|---|
| One-line schema bootstrap | Reproducibility and review beat convenience. |
| Models as the single source of truth | Migrations win when they disagree. Models exist to make the app pleasant to write. |
| Perfect autogenerate | We treat it as a draft. That is the documented Alembic posture, not a workaround. |

## What would change this later

- A dedicated DBA / schema-management product (e.g. Atlas, Liquibase) if the team grew and wanted SQL-first migrations.
- If we dropped Postgres-specific types, autogenerate would become trustworthy enough to use with less review — still not zero review.
